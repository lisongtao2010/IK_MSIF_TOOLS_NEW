## 输出规则
- 只输出核心代码、终端命令或直接解决方案。
- 禁止解释代码原理，禁止输出修改前后的对比废话，除非我明确要求解释。
- 除非存在严重报错风险，否则不提供额外建议或拓展阅读。
## 执行规范
1. **最小化修改**：只修改与当前问题直接相关的代码行，严禁顺手格式化或重构未提及的周边代码。
2. **先读后改**：修改前必须完整读取目标文件上下文，避免破坏现有类型或导入。
3. **验证闭环**：修改完成后，自动运行项目的类型检查或单测命令验证（如 `npm run typecheck` 或 `pytest`）。
4. **极简回复**：只输出修改了哪个文件的哪几行及验证结果，禁止输出大段代码解释。
## 排错流程
1. **定位根因**：先根据报错信息定位具体文件和行号，阅读相关代码，不要凭空猜测。
2. **禁止掩盖错误**：严禁通过删除测试用例、加 `try-except: pass` 或使用 `@ts-ignore` / `any` 来绕过报错。
3. **三振出局原则**：如果同一修复方案连续失败 2 次，立即停止继续尝试，向用户汇报已排查的路径和当前阻塞点。
## 提交规范
1. 先执行 `git status` 和 `git diff --staged` 检查实际变更内容。
2. 严格遵循 Conventional Commits 格式：`<type>(<scope>): <简短中文或英文描述>`（type 仅限 `feat`、`fix`、`refactor`、`docs`、`chore`、`test`）。
3. 标题控制在 50 字符以内，直接给出可直接执行的 `git commit -m "..."` 命令。
