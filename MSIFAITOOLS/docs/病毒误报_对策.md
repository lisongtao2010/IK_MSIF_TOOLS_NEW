# 病毒误报 / SmartScreen 拦截 对策

> 面向：把 `MSIFAITOOLS.exe` 分发给客户 / 现场人员时，被 Windows Defender、SmartScreen
> 或第三方杀毒软件拦截（「Windows 已保护你的电脑」「Trojan:Win32/Wacatac.B!ml」等）。
> 本文分两部分：**为什么会误报**（第 1 章）、**要做什么**（第 2〜7 章）。

---

## 1. 根因

误报不是单一原因，而是「未签名 + 信息不全 + 可疑打包方式 + 可疑行为」叠加到机器学习
打分模型上的结果。按影响从大到小：

| # | 现象 | 影响 | 误报检测点 |
|---|------|------|-----------|
| 1 | exe **没有数字签名**（`Get-AuthenticodeSignature` = `NotSigned`） | ★★★★★ | SmartScreen 对新 exe 一律拦；Defender 对「未知发布者」加分 |
| 2 | 版本信息不全：`CompanyName` 为空、`LegalCopyright` 格式错乱 | ★★★ | 「伪装成正常软件的手工编译程序」特征 |
| 3 | 分发的是 **Debug 构建 + `.pdb`** | ★★★ | 未优化代码 + pdb 里的源码绝对路径（含用户名）＝典型恶意样本形态 |
| 4 | 包里带 `OpenCvSharpExtern.dll`(61 MB)、`opencv_videoio_ffmpeg4100_64.dll`(26 MB) | ★★★ | 这两份原生库被大量挖矿木马 / 下载器打包，静态特征重叠 |
| 5 | 行为：`Process.Start("explorer.exe", ...)`、`Process.Start(cmd)`、写临时目录、拉起子进程 | ★★ | 「下载器 / 载荷投递」启发式 |
| 6 | 每次发版都换新 hash，下载量小，无信誉积累 | ★★★ | SmartScreen 信誉按 **文件 hash + 签名主体** 累计 |
| 7 | 文件带 Mark-of-the-Web（浏览器下载 / 邮件 / 内网共享都会带） | ★★ | 有 MOTW 且无签名 → SmartScreen 必弹 |

> 说明：第 4 条那个 OpenCvSharp 依赖是「把分割源码链接进主程序」时期的遗留，
> 主程序代码里没有任何 `OpenCvSharp` 引用（分割功能现在调外部 `CadPartSplitter.exe`），
> 已于 2026-11 从 `MSIFAITOOLS.csproj` 删除。

## 3. 标准发布流程

**最省事：双击项目根目录的 `发布.bat`**。它等于下面这条命令（自动选自签证书、自动附带信任材料）：

```powershell
.\Tools\Publish-Signed.ps1 -SelfSigned
```

要指定证书 / 精细控制时：

```powershell
cd <仓库>\MSIFAITOOLS

# 正式发布（用代码签名证书，运行时会提示输入密码）
# 注意：工程里现存的 msif.pfx 是强名称密钥，签不了 Authenticode —— 见第 4 章
.\Tools\Publish-Signed.ps1 -CertificatePath .\code-signing.pfx

# 证书已装进「个人」证书存储时，按 SHA-1 指纹签名（推荐：硬件 token 只能这样签）
.\Tools\Publish-Signed.ps1 -CertificateThumbprint 1A2B3C4D5E6F...

# 只验证流水线（不签名，仅内部测试用）
.\Tools\Publish-Signed.ps1 -SkipSign
```

产物：`artifacts\publish\MSIFAITOOLS_<版本>_<时间>\` 与同名 `.zip`。

要点：

* **对外发布绝不能用 `-SkipSign`**，也不要用 `bin\Debug` 直接打包。
* 包里会自动剔除 `*.pdb` / `*.xml` / `*.db*` / `*.log` / `*.tmp`。
* 脚本会做自检：主程序本体体积异常（> 60 MB）或缺少 `CadPartSplitter\` 时会给出警告。
* 签名前会先校验证书（Code Signing EKU / 私钥 / 有效期），不符合就当场报错并说明原因。
* 「发布信息.txt」里有版本、构建时间、签名主体、**每个文件的 SHA-256** —— 提交误报时必须附上。
* zip 旁边还会生成 `<包名>_误报提交材料\`（英文/日文提交正文 + 哈希清单 + 3 个提交入口），被报毒时照抄即可。
* 包里 `MSIFAITOOLS.exe.config` 里的 `AiApiKey` 默认会被清空（`-SecretMode`）——但**程序内有内置测试密钥兜底**（`Services\AiApiOptions.DefaultApiKey`）：
  只要接口地址还是 ModelArts `/v2`，【AI 设置】会自动带出测试 Key、AI 分析照常可用；换成别的接口地址才会要求自己填 Key。
  给公司外时加 `-SecretMode BlankAll` 连 SQL 密码一起清 —— 细节见 `docs\交付给别人_检查清单.md`。

验证签名（拿到包后自己先查一遍）：

```powershell
Get-AuthenticodeSignature .\MSIFAITOOLS.exe | Format-List Status,SignerCertificate
& "$env:ProgramFiles(x86)\Windows Kits\10\bin\<版本>\x64\signtool.exe" verify /pa /v .\MSIFAITOOLS.exe
```

`Status` 必须是 `Valid`；`SignerCertificate.Subject` 必须是公司真实名称（`CN=...`）。

## 4. 代码签名证书：`msif.pfx` 已核实不能用

### 4.1 核实结论（2026-11-25 在本机实测）

**`msif.pfx` / `cad.pfx` 都是「强名称（strong name）密钥」，不是 Authenticode 代码签名证书。
拿到密码也签不出客户机信任的签名 —— 这条路不必再花时间。**

| # | 核实项 | 实测结果 | 说明了什么 |
|---|--------|----------|-----------|
| 1 | 工程里的角色 | `MSIFAITOOLS.csproj` 第 65 行 `<AssemblyOriginatorKeyFile>msif.pfx</AssemblyOriginatorKeyFile>` 且 `SignAssembly=false`；`CadPartSplitter.csproj` 同样指向 `cad.pfx` | 这两个 pfx 的用途是**强名称签名**，与 Authenticode 无关 |
| 2 | 密码 | 59 个常见候选（`msif` / `MSIF2010` / `cad` / `123456` / 空密码 …）全部失败；docs、csproj、ps1、git 历史里都没有记录 | 这是本机一次性生成的测试密钥，不是团队保管的发布密钥（发布密钥的密码一定会安全保存） |
| 3 | 包结构 | 1764 字节；ASN.1 里只有 1 个 `encryptedData`（证书 + 私钥整体加密），无明文证书、无中间 CA | 单张自签名证书 + 一个私钥，正是 VS「创建测试证书」的产物形态；真实 CA 代码签名 pfx 通常 3 KB 以上并带证书链 |
| 4 | 本机证书存储 | `Cert:\CurrentUser\My`、`Cert:\LocalMachine\My` 中**没有任何带 Code Signing EKU（1.3.6.1.5.5.7.3.3）的证书** | 这台机器从未做过 Authenticode 签名 |
| 5 | 两个文件的关系 | SHA-256 不同（`msif.pfx`=EDA6768D…、`cad.pfx`=C115AA3D…），但大小**都正好 1764 字节** | 同一工具、同一套默认参数生成的两个测试密钥 |

顺带的处理建议：

* **私钥已挡在 git 外**：根目录 `.gitignore` 里的 `*.pfx` / `*.snk` 已由注释改为生效。两个历史文件
  仍在版本库中，需要时可以 `git rm --cached MSIFAITOOLS/msif.pfx CadPartSplitter/cad.pfx` 移出
  （本机留一份即可，删掉不影响构建，因为 `SignAssembly=false`）。
* 发布脚本已内置预检：`-CertificatePath` / `-CertificateThumbprint` 指定的证书若缺少
  Code Signing EKU、没有私钥或已过期，会**在签名前直接报错并说明原因**，不会再出现
  signtool 那句「证书不满足所有条件」。

### 4.2 拿到新证书后先验一遍（别等到打包现场才发现不能用）

```powershell
$cert = Get-PfxCertificate .\code-signing.pfx      # PS 5.1 没有 -Password，会弹窗输入
$cert | Format-List Subject, Issuer, NotBefore, NotAfter, Thumbprint, HasPrivateKey
$cert.Extensions | Where-Object { $_.Oid.Value -in '2.5.29.37','2.5.29.15' } | ForEach-Object { $_.Format($true) }
```

判定标准：

| 检查项 | 必须满足 | 不满足会怎样 |
|--------|----------|--------------|
| 扩展密钥用法 EKU `2.5.29.37` | 含 `1.3.6.1.5.5.7.3.3`（Code Signing） | signtool 直接拒绝（本仓脚本会先拦住并说明） |
| 密钥用法 KeyUsage `2.5.29.15` | 含 `Digital Signature` | 同上 |
| 私钥 | `HasPrivateKey = True`（EV / token 证书要插着 token） | 签不了名 |
| `Issuer` | 公共 CA（DigiCert / Sectigo / GlobalSign / SSL.com …）或公司内部 CA（域机信任） | 自签名 → 客户机上依然当未签名 |
| `Subject` | 公司真实名称（OV/EV 需企业验证） | SmartScreen 不认发布者 |

### 4.3 现在可以走的几条路

本次核实还发现：本机「受信任的根证书颁发机构」里有 `CN=lixil-CA, DC=lixil, DC=lan`（两张）和
`CN=jpn-CA, DC=jpn, DC=ithd, DC=local` —— **公司自己有 AD CS 内部 CA**，这条路免费且当天可用。

但这个 CA 同时说明了「为什么只能找 IT」（2026-11 实测）：

* AD 里查 `objectClass=pKIEnrollmentService` 结果是 **0 条** → 企业 CA 没发布到域，没有自助申请入口；
* `lixil-CA` 证书里没有 AIA / CRL 分发点扩展，`http://<CA服务器>/certsrv/` 也不是申请页 → 属于独立（standalone）CA；
* 本机和仓库里没有任何可用的代码签名证书（磁盘上只有那两个强名称 pfx；仓库 `bin\` 下 75 个 exe 全部 `NotSigned`）。

所以现在要做的不是「找证书」，而是「发起申请」——CSR 和申请话术已经准备好，见
[代码签名_IT申请.md](代码签名_IT申请.md)（含日文 / 中文两版可直接转发的原文）。

| 方案 | 费用 | SmartScreen 效果 | 说明 |
|------|------|------------------|------|
| **公司内部 CA 的代码签名证书**（推荐先做） | 0 元（IT 出证） | ✅ 域内机器不再显示「未知发布者」；内网分发（无 MOTW）不会弹 SmartScreen | 让 IT 按 **Code Signing** 模板签一张，拿到后在证书存储里用 `-CertificateThumbprint` 签。前提：客户机在域内并信任该 CA |
| OV 代码签名证书 | ≈ 1,500〜3,500 元/年 | ⚠️ 需靠下载量累积信誉 | 2023-06 起 CA/B 规定私钥必须在**硬件 token / HSM** 里，一般无法导出 `.pfx` → 用 `-CertificateThumbprint` 签 |
| EV 代码签名证书 | ≈ 3,000〜6,000 元/年 + token | ✅ 立即获得信誉（免 SmartScreen 弹窗） | 对外分发、预算允许时首选 |
| Azure Trusted Signing | ≈ US$9.99/月 | ✅ 等同于 CA 签发 | 云签名、无需 token；要求组织有 3 年以上可查历史，且目前面向美/加/欧实体，日本/中国法人能否过审需先确认 |

申请材料已经做成脚本，一条命令生成 CSR（**私钥不出本机**，只把 `.req` 发出去）：

```powershell
# 第 1 步：生成请求 → artifacts\codesign\codesign.req（+ codesign.inf 参数说明）
.\Tools\New-CodeSigningRequest.ps1

# 第 3 步：IT 把 .cer 发回来后 → 校验 EKU、装证书、导出 code-signing.pfx
.\Tools\New-CodeSigningRequest.ps1 -CertificateFile .\codesign.cer

# 若 IT 愿意给「CA服务器名\CA名」和模板名，第 2 步可以一条命令直接提交并收回
.\Tools\New-CodeSigningRequest.ps1 -CaConfig 'CAHOST\lixil-CA' -Template CodeSigning
```

给 IT 的**完整申请原文（日文 / 中文两版，可直接复制转发）**在
[代码签名_IT申请.md](代码签名_IT申请.md) 第 3 章；需要 IT 回答的 4 个问题（CA 配置串、模板名、
有效期、是否允许外部时间戳）在该文 3.3 节。

### 4.4 「免费的证书」到底有没有（2026-11 核实）

结论：**公网上已经没有可以免费申请的代码签名证书**。免费的只剩两条：**公司内部 CA**（本章主方案，
需 IT 出证）和**自签证书**（`Tools\New-SelfSignedCodeSigningCert.ps1`，只够内部/测试用）。

| 看起来免费的 | 实际情况 |
| --- | --- |
| Let's Encrypt / ZeroSSL / Buypass / Google Trust Services | 只签 TLS 证书（EKU = `serverAuth`）。里面没有 Code Signing EKU，`signtool` 直接拒绝；签发时校验的是域名控制权，和代码签名无关。 |
| SignPath.io 免费额度 | 只给**公开开源**项目：仓库必须 public、许可证要审核、人工批准。公司内部工具不满足。 |
| Certum / Sectigo 的开源代码签名 | 同样要求开源项目证明 + 个人实名 + 人工审核，周期以周计，且只覆盖开源制品。 |
| 各类「CI 免费签名」模板 | 本质都是上面两类 OSS 额度，或者就是自签。 |
| Azure Trusted Signing | 收费（≈ US$9.99/月），且要求组织有 3 年以上可验证历史。 |
| 自签证书（本仓库脚本） | 真免费、真能签，但**只对自己机器 / 装了根证书的域内机器有效**，不能对外分发。 |

自签证书实测结论（2026-11-25 本机）：

```powershell
# 生成：RSA 3072 / 3 年 / Code Signing EKU / 导出 pfx（签名用）+ cer（GPO 部署根证书用）
.\Tools\New-SelfSignedCodeSigningCert.ps1

# 用指纹签名发布（时间戳照常走 DigiCert）
.\Tools\Publish-Signed.ps1 -CertificateThumbprint <指纹>
```

* 签名本身完全正常：`SignatureType = Authenticode`，带 DigiCert RFC3161 时间戳；
* 在**没装根证书**的机器上 `Get-AuthenticodeSignature` 是 `UnknownError`（链终止于不受信任的根）——
  这不是签名坏了，是信任问题；
* 把导出的 `msif-codesign-root.cer` 装进「受信任的根证书颁发机构」后立刻变 `Valid`
  （已实测：装 → `Valid`，撤掉 → `UnknownError`，证书存储无残留）；
* 所以自签证书的正确用法只有三个：**域内用 GPO 分发根证书**、**随包让接收人自装根证书**（见 4.5）、
  或**只在测试机验证签名流水线**。对公网用户毫无作用（没人会装你的根证书），SmartScreen 该弹还弹。

`Publish-Signed.ps1` 遇到「签名已写入但根证书不受信」时**只警告、不中断打包**，并把
`签名状态 : UnknownError（签名已写入，但根证书在本机不受信）` 写进「发布信息.txt」，
避免误以为「签了名就免 SmartScreen」。

### 4.5 不找 IT 的路线：自签 + 随包「信任发布者」（2026-11-25 实现并实测）

内网 CA（`代码签名_IT申请.md` 的主方案）必须由 IT 签发 —— **CA 私钥只存在于 CA 服务器/HSM，
除 IT 之外没人能签出被域信任的证书**，这是 PKI 的设计前提，不是流程上的麻烦。

如果不想走这个流程，可以走完全自助的一条路：

```powershell
# 1) 生成自签代码签名证书（只做一次，RSA 3072 / 3 年 / Code Signing EKU）
.\Tools\New-SelfSignedCodeSigningCert.ps1

# 2) 签名打包，并把「信任发布者」材料一起打进包里
.\Tools\Publish-Signed.ps1 -CertificateThumbprint <自签证书指纹> -IncludeTrustedPublisher
```

包里会多出四个文件：

| 文件 | 作用 |
| --- | --- |
| `安装信任_双击我.bat` | **接收人只需要双击这个**：调用下面的 ps1，指纹已写死在命令行里（cer 被替换会当场报错），不需要管理员 |
| `trusted-publisher.cer` | 本次签名证书的公钥部分（不是 pfx，不含私钥） |
| `Install-TrustedPublisher.ps1` | 实际干活的脚本：把 cer 加进**当前用户**`\Root`，**不需要管理员** |
| `先装信任_再运行.txt` | 给接收人的说明，含主体 / 指纹 / cer 的 SHA-256，便于核对没被替换 |

接收人做法（一次性）：**双击 `安装信任_双击我.bat`**（最省事）；
也可以右键 ps1 →「使用 PowerShell 运行」，或 `powershell -ExecutionPolicy Bypass -File .\Install-TrustedPublisher.ps1`；
撤销：`安装信任_双击我.bat -Uninstall`（或 ps1 后面加 `-Uninstall`）。**撤销时 Windows 会弹一次
「ルート証明書ストア」确认框，点「はい / 是」才会真删掉；安装时不会弹任何框。**

实测（2026-11-25，包内脚本 / bat 直接跑）：未信任状态下双击 bat → 退出码 0、`Cert:\CurrentUser\Root`
无→有、`Get-AuthenticodeSignature` 从 `UnknownError` 变 `Valid`、窗口打印 `[OK] Finished`；
再双击一次 → 「已经装过了」仍退出码 0；缺 `trusted-publisher.cer` 或 ps1 → 打印 ERROR 并以退出码 1 结束；
`-ExpectedThumbprint` 给错时脚本拒绝安装并以退出码 1 结束；`-SkipSign` 打包时该开关只会提示跳过。

必须知道的限制：

* **只能在公司内部分发**。不要要求外部客户安装你的根证书 —— 那等于让他们信任一个可以签任意
  程序的私有根，安全上说不通，对方 IT 也不会批；
* 装信任只解决「未知发布者 / 签名校验」，**不提高 SmartScreen 信誉分**：从浏览器或邮件下载
  （带 Mark-of-the-Web）仍可能被拦一次，走内网共享 / U 盘 / 软件分发系统才干净；
* 每台机器要装一次。如果嫌麻烦，把 `msif-codesign-root.cer` 交给 IT 导入域组策略（一次性全公司
  生效）—— 但那是「导入一张根证书」，比「给你个人签一张证书」容易批得多，是完全不同的流程；
* 私钥只在这台机器上：换机 / 重装系统后要重新生成，指纹会变，`trusted-publisher.cer` 要重新分发，
  旧的那份记得在接收机上 `-Uninstall` 掉。


暂时没有证书时的务实做法：**别让客户从浏览器/邮件下载**，改成内网共享目录、
公司软件分发（Intune / GPO / 共享盘）或 U 盘拷贝 —— 没有 Mark-of-the-Web 就不会触发
SmartScreen 弹窗（但 Defender 仍可能报毒，所以第 5、7 章照样要做）。

## 5. 提交误报（免费、最有效，必须先做）

签名解决「未知发布者」，提交误报解决「已经报毒的具体特征」。两者不能互相替代。

> **材料已经自动生成好了**：每次打包（`Publish-Signed.ps1` 或双击 `发布.bat`）都会在 zip 旁边
> 生成 `<包名>_误报提交材料\`：
>
> * `01_怎么提交.txt` —— 3 个入口（Microsoft WDSI / VirusTotal 各厂商 / 公司内部按哈希加白）+ 具体点法；
> * `02_提交正文_EN.txt`、`03_提交正文_JP.txt` —— 正文已写好，只剩「检测名称」一个空位要填；
> * `04_哈希清单.txt` —— 两个 exe 的 SHA-256 + 整包哈希，直接发给公司信息安全就能加白。
>
> 也就是说**被报毒时你不需要写任何东西**，照 `01` 点一下、粘一下就行。

### 5.1 Microsoft（Defender + SmartScreen）

1. 打开 <https://www.microsoft.com/en-us/wdsi/filesubmission>
2. 选择 **「I am a software developer」**（开发者通道）→ **「Incorrectly detected as malware」**
3. 上传**被报毒的那个文件**（一般是 `MSIFAITOOLS.exe`；必要时整个 zip，超过大小限制时给下载链接）
4. 说明里写明：
   * 检测名称（如 `Trojan:Win32/Wacatac.B!ml`）
   * SHA-256（从「发布信息.txt」复制）
   * 公司名、程序用途、是否为内部业务工具
   * 程序为什么有那些行为（例如「会拉起同目录下的 CadPartSplitter.exe 做 PDF 分割」）
5. 一般 24〜72 小时出结果；同一 hash 重新提交会更快。

> SmartScreen 的「已保护你的电脑」走同一个入口（属于 Defender SmartScreen 判定）。
> 提交后若仍弹窗，多半是**信誉还没累积**，继续按第 6 章做。

## 6. 信誉累积（让 SmartScreen 自己放行）

* **同一个证书主体连续发版**，不要换证书、不要换 exe 文件名。
* **减少无意义的 hash 变化**：提示语等资源走 exe 内嵌 + 运行时可编辑，别每次微调都重新发布。
* **扩大运行量**：先在内部几十台机器上正常安装运行（签名有效 + 多个终端运行 → 信誉涨得很快）。
* **固定分发位置**（同一个共享目录或同一个网址），别每次换路径。
* 版本升级时**沿用同一套版本信息模板**（Company / Product / Copyright 不要来回改）。

## 7. 行为侧降误报（后续可做，按收益排序）

1. **避免字符串拼接命令行**：优先 `ProcessStartInfo.ArgumentList`（.NET Framework 4.8 没有，
   那就用 `Arguments` 属性，而不是 `Process.Start(file, "拼接串")`）。
2. **`explorer.exe` 打开目录**（`Form1.cs`、`PartBasicInfoForm.cs`、`AiSettingsForm.cs` 里有
   `Process.Start("explorer.exe", "\"" + path + "\"")`）改成
   `Process.Start(new ProcessStartInfo(path) { UseShellExecute = true })`，
   不显式拉 explorer.exe，减少「下载器」特征。
3. **不要写随机临时文件**：中间产物统一落到固定目录（如 `D:\MSIFDB\...`、输出目录下的 `classify\`）。
4. **不要自解压 / 自复制 / 动态生成 exe / 反射加载**（本项目目前没有，保持）。
5. 子进程（`CadPartSplitterRunner`、`ClaudeCodeCliClient`）已经用
   `UseShellExecute=false` + `CreateNoWindow=true`，保持现状即可；注意别再叠加 `cmd.exe /c`。
6. 升级 exe 时**保持文件名不变**，别出现 `MSIFAITOOLS_new.exe`、`MSIFAITOOLS(1).exe` 之类。

## 附：常见问题

**Q：签了名为什么还弹 SmartScreen？**
A：OV 证书不等于「免弹窗」，它只是把「未知发布者」变成「已知发布者」，信誉仍需累积；
EV 证书才会立即放行。另外确认签名带了时间戳（`signtool /tr`），否则证书一到期签名全部失效。

**Q：客户机上的旧版被 Defender 删了怎么办？**
A：先把被删文件提交误报（第 5 章），同时在客户机上临时加排除项
（Defender →「病毒和威胁防护」→「排除项」加程序目录），等厂商更新特征后再撤掉。

**Q：能给整个 zip 签名吗？**
A：不能，Authenticode 只对 PE 文件（.exe/.dll）有效。zip 只用于分发，签名要做在里面的 exe 上。
